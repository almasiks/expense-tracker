## Scoring legend

Context: single-user local CLI, personal finance data in one JSON file, public GitHub repo.

| Score | Likelihood (L) | Impact (I) |
|-------|----------------|------------|
| 1 | Needs an unusual action or event (rare typo, crash during a write, deliberate odd input) | Inconvenience; obvious to the user, nothing lost (e.g. a traceback, a dev tool missing) |
| 2 | Can happen in normal use now and then (a typo, a habit, a fresh clone, an agent session) | Wrong numbers or a broken report the user may not notice; data still recoverable |
| 3 | Happens in ordinary use, almost unavoidable | Loss/corruption of the data file, or personal finance data exposed publicly |

Score = L × I (1–9). Unsupported findings: score "—", not mitigated.

## Top two Confirmed risks for corrective action (Task 07)

**1. R1 — duplicate IDs (score 6).** **2. R2 — amount validation (score 4).**

R1 has the joint-highest score and the smallest possible fix: one line in `_next_id`, verified by a
single deterministic pytest, with no change to file formats or existing tests. R2 is the next
highest-scoring code defect, was already documented at baseline (W4, `evidence/05`), and is fixed
locally in `add_expense` plus a parametrized test, so both stay "one focused change per commit".
R4 also scores 6 but was not picked because its fix spans two components (atomic writes in
`storage.py` plus an export-path guard in `exporters.py`/`service.py`) and the crash path can only be
tested by simulation — it deserves its own task. R8 (score 6) was not picked because its mitigation is
configuration and an agent rule, not a code fix verifiable by pytest; it is cheap enough to apply as a
separate housekeeping commit. R3, R5a and R7 (score 4) need more design decisions (date/month
contract, intentionally changing a pinned characterization test, CLI test harness).
